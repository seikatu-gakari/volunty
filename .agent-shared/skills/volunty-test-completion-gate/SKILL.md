# テスト完了判定

変更した挙動と利用者への影響に対して、十分な検証証拠を揃える。既存テストが必要なケースをassertしていれば、そのテストを使う。追加・更新はカバレッジが不足する場合に行う。

| 変更 | 必要な検証 |
| --- | --- |
| ドメインロジック、Server Action、バリデーション、状態遷移 | 分岐・境界値・失敗経路のUT。ユーザーフローも変わる場合はE2E |
| フォーム、ルート、認証・権限、複数ロールのフロー | 影響するフローのE2Eと、分岐・変換ロジックのUT |
| UIの見た目・文言だけ | 該当画面の表示確認。操作・アクセシビリティ・状態分岐に影響する場合は該当テスト |
| DB schema、migration、外部I/O | 影響する契約・統合経路の検証。決定的なロジックはUT、ユーザーフローの変更はE2E |
| 振る舞いを維持するリファクタリング | 影響する既存の回帰テスト。不足するケースだけ追加・更新 |
| ドキュメント、instructionsだけ | 内容・参照・必要な構文検証。アプリのUT/E2Eは原則不要 |
| テストだけ | 変更したテストの実行。テスト基盤の変更ではその影響範囲も確認 |

## 証拠を揃える

- 要件と差分から影響する挙動を特定し、既存テストのassertと照合する。
- バグ修正では再現テスト、新しい挙動では期待する結果のテストを用意し、可能なら修正前の失敗と修正後の成功を確認する。振る舞い不変の変更のためにREDを作らない。
- 対象テストから実行し、共有処理・設定の影響や失敗がある場合に範囲を広げる。PRのrequired checksは変更規模によらず満たす。
- 成功結果は対象コード・検証環境と結び付ける。新しい変更や未解決の懸念がなければ、commit・レビュー・報告の各段階で同じ検証を繰り返さない。変更後は影響する範囲を再実行する。
- 必要なE2Eがローカルで実行できない場合は、同じPRの最新HEADに対するCI E2Eで確認できる。環境の制約、CI結果、残る確認事項を分けて記録する。必要な検証が未実行・失敗・待機中なら検証完了とはしない。

コマンドが必要なら [volunty-dev-commands](../volunty-dev-commands/SKILL.md) を参照する。使い捨ての専用環境と確認できるテストは、依頼に起因する失敗の修正・再実行まで手順ごとの承認なしで進める。本番接続や共有データのresetを推測で実行しない。

報告には実行結果と、追加不要・適用外・未実行の理由を簡潔に含める。表は複数区分を比較するときに使う。
