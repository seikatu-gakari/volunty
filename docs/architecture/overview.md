# アーキテクチャ概要

## 1. システム全体像
- **提供価値**: 性格診断に基づき、ボランティア希望者と団体の相性を可視化し、マッチングを効率化する。
- **主要ユースケース**:
	- 参加者が性格診断を受け、相性の良い団体を知る。
	- 団体が募集情報を登録し、適した参加者を推薦される。
	- 管理者が全体のマッチング状況をモニタリングする。
- **外部依存**: OAuth プロバイダ(Google/LINE)、将来的な東京アプリ API、LINE 公式アカウント。

## 2. モジュール構成
- **Next.js アプリ (TypeScript)**: UI プレゼンテーションとルーティング。App Router 採用予定。MUI によるコンポーネントスタイル、Storybook でカタログ化。
- **状態管理レイヤ**:
	- **Jotai**: グローバルかつ軽量な状態共有。ユーザーセッション、診断回答、フィルタなどを管理。
	- **XState**: 性格診断フローなど状態遷移が複雑な機能をステートマシンで制御。
- **フォームバリデーション**: React Hook Form + Yup。診断回答や応募フォームのバリデーションを共通化。
- **データアクセス**: API クライアント(REST/GraphQL TBD)を `services/` に集約。型安全性のため OpenAPI 生成 or zod/yup スキーマを検討。
- **バックエンド**: 現時点では未決。想定はサーバレス API か Node/NestJS。決定後、本セクションを更新。

## 3. データフローとストレージ
- **フロント内データフロー**:
	1. Next.js サーバコンポーネントが初期データを取得。
	2. クライアントコンポーネントで Jotai アトムに注入。
	3. XState マシンが診断ステップの遷移と副作用(API呼び出し)を管理。
- **診断データ**: 回答送信時に API へ POST、結果を受け取り Jotai へ保持、画面描画。
- **マッチングデータ**: 団体・募集情報を API 経由でフェッチ、スコア付き候補を一覧に表示。
- **ストレージ**: 永続化層(DB) はバックエンドにて管理。フロントではブラウザ保存を限定的に利用 (例: localStorage にセッション中の回答を一時保存)。

## 4. AI 活用領域
- **ボランティア推薦 AI**: 診断結果・活動履歴・応募状況を特徴量としてスコアリング。MVP ではルールベース、Phase 2 以降で協調フィルタリングや LLM による説明生成を検討し、推論は AWS Bedrock 等のマネージドサービスを利用する。
- **団体向け振り返り分析 AI**: 団体の活動レポートと参加者フィードバックを Bedrock 経由の LLM が要約し、改善提案・参加者向けメッセージ案を生成。PII は事前にマスキングし、出力は担当者が承認する。
- **運用ガードレール**: 入出力ログを保存し、生成結果の編集率や採用率を KPI として追跡。誤生成時に手動ロールバックできるようヒューマンレビューを必須とする。自前のディープラーニング学習は行わず、モデル管理・バージョンは Bedrock 側の仕組みを活用する。

## 5. 非機能要件
- **パフォーマンス**: Next.js の SSR/SSG を活用し、初回表示 < 2.0 秒 (モバイル回線での 75 パーセンタイルを目標)。
- **アクセシビリティ**: MUI コンポーネントに準拠しつつ、WCAG 2.1 AA を目指す。Storybook で a11y アドオンを使用。
- **セキュリティ**: OAuth トークンは Secure/HttpOnly Cookie で保持。フォーム入力は Yup でバリデーション。PII を扱う画面ではマスキングを検討。
- **観測性**: フロント側のエラートラッキング(Sentry 等)とユーザ操作ログ(KPI 計測)の導入を検討。

## 6. テスト戦略
- **ユニットテスト**: Vitest + Testing Library。Jotai アトム、XState マシン、ユーティリティを対象。
- **コンポーネントカタログ**: Storybook + Storybook Test Runner を用い、UI のスナップショット/視覚回帰を検討。
- **統合テスト**: Vitest で API モックを使った画面単位テスト。重要フローは Playwright/Cypress で E2E を追加検討。
- **CI/CD**: GitHub Actions で lint (ESLint), type-check (tsc --noEmit), unit test (vitest run) を最小構成として実施。

## 7. 今後の課題と決定事項
- **バックエンド技術選定**: NestJS/Express/Serverless 等を比較検討し、決定次第ドキュメント更新。Decision Log へ記録。
- **API 仕様確定**: スキーマ駆動(OpenAPI)か tRPC かを議論。確定後に `services` レイヤの実装方針を追記。
- **東京アプリ連携**: 提供 API の認証方式・レート制限を確認。独立アダプタの設計が必要。
- **画像生成/LINE 連携**: Phase 2 以降で利用する外部サービス候補を調査し、セキュリティ・コストを評価。
- **フィードバック窓口**: 現状は GitHub Issues。運用方針を `.github/knowledge-base/process-guide.md` に沿って明記し、必要なら Slack / Discord を追加。
