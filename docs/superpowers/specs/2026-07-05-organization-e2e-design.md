# 団体向けE2Eテスト拡充 設計書

## 目的

GitHub Issue #167 に基づき、既存の団体向け Playwright E2E `O1`〜`O3` を維持したまま、団体オンボーディング、審査ライフサイクル、案件管理、参加者へのアプローチ、応募管理、活動完了、証明書審査を `O-E1`〜`O-E10` として追加する。

テストはローカル Supabase とテスト認証ルートだけを使用し、本番・Vercel Preview・Google OAuth・メール送信には接続しない。

## 採用方針

変更系テストによる状態汚染を防ぐため、団体の用途ごとに専用ペルソナと専用レコードを割り当てる。`seed:e2e` は各テスト実行前に Auth、団体審査、案件、応募、アプローチ、証明書を決定的な初期状態へ戻す。

O-E9 で要求される活動完了履歴については、既存のマッチング履歴機能が `accepted` と `declined` だけを取得し、既存ステータス `completed` を除外している。新機能は追加せず、既存履歴機能の状態漏れ修正として `completed` の取得・表示を追加する。

## ペルソナ

既存の `organization-approved` と `organization-pending` は既存 O1〜O3・管理者 E2E のために維持し、次を追加する。

| ペルソナ | 用途 | seed 初期状態 |
| --- | --- | --- |
| `organization-fresh` | O-E1 オンボーディング | Auth と `m_user` のみ。role 未設定、オンボーディング未完了、団体プロフィールなし |
| `organization-reapply` | O-E2 否認後の再申請 | 否認理由と完全な入力値を持つ `rejected` 団体 |
| `organization-profile-review` | O-E3 承認済みプロフィール編集 | 完全な入力値を持つ `approved` 団体 |
| `organization-lifecycle` | O-E4〜O-E10 の変更系フロー | `approved` 団体と変更専用レコード |
| `organization-foreign` | 所有権境界用 | lifecycle 団体とは別所有者の `approved` 団体・案件 |

`auth.setup.ts` は各ペルソナの storage state を個別ファイルへ保存する。変更系ケースは `organization-lifecycle` のみを使い、読み取り中心の `organization-approved` や既存 O1〜O3 のデータを変更しない。

## Seed 設計

`app/scripts/seed-e2e.ts` に団体 E2E 用の固定データを追加する。

- fresh 団体がテストで作成したプロフィールを削除し、Auth metadata を未選択状態へ戻す。
- reapply 団体を `rejected`、固定の否認理由、完全なフォーム初期値へ戻す。
- profile-review 団体を `approved`、`verified=true`、完全なフォーム初期値へ戻す。
- lifecycle 団体を `approved` とし、案件作成・編集・終了、応募辞退・完了、アプローチ送信、証明書承認・却下の専用レコードを復元する。
- foreign 団体と案件を lifecycle 団体とは別の所有関係で upsert する。
- おすすめ参加者の順序を決定的に検証できるよう、公開・診断済み参加者と案件要求特性に差を持たせる。
- アプローチ履歴用に `sent`、`accepted`、`declined`、期限切れの4状態を別レコードで復元する。
- 証明書承認用と却下用の `pending` 申請を別レコードで復元する。
- 送信テスト用アプローチは seed ごとに削除し、同一参加者・案件への初回送信を再現する。

seed のユニットテストは呼び出し回数だけでなく、各ペルソナと変更専用レコードの初期化値を検証する。

## E2E 構成

既存 `app/e2e/organization.spec.ts` の O1〜O3 は変更せず維持する。追加ケースは責務で2ファイルに分ける。

### `organization-onboarding.spec.ts`

- `O-E1`: 団体ロール選択、必須情報と LINE 連絡先入力、登録、審査待ち表示
- `O-E2`: 否認理由表示、登録内容修正、再申請、審査中への復帰
- `O-E3`: 承認済みプロフィール編集、審査中への復帰、ダッシュボード制限

### `organization-lifecycle.spec.ts`

- `O-E4`: 詳細項目付き案件作成、編集反映、募集終了
- `O-E5`: おすすめ参加者の相性スコア順、一覧・詳細情報
- `O-E6`: メッセージ付きアプローチ送信、履歴反映、重複送信抑止
- `O-E7`: 未回答、承諾済み、辞退済み、期限切れの履歴表示
- `O-E8`: 応募メッセージ・診断情報・BIG5 の詳細表示、応募辞退
- `O-E9`: 承認済み応募の活動完了、承認・辞退・活動完了の履歴表示
- `O-E10`: 別々の申請に対する証明書承認・番号発行、理由付き却下

テスト名には必ず `O-E1`〜`O-E10` を含める。固定時間待機、CSS クラス依存セレクタ、テスト間の実行順依存は使用せず、role・label・heading・URL・利用者向けテキストで待機と検証を行う。

## O-E9 の最小アプリ修正

既存 `fetchMatchingHistory()` の対象状態と履歴表示型に `completed` を追加する。表示ラベルは既存応募画面と合わせて `活動完了` とし、既存の `承認済み`・`辞退済み`を維持する。

修正前にユニットテストで、`completed` が取得条件に含まれ、履歴データへ変換されることを RED として確認する。E2E では変更専用応募を活動完了へ更新後、履歴画面に案件名と `活動完了` が表示されることを検証する。

## エラー処理と安定性

- 各変更系ケースは専用レコードだけを変更する。
- seed は2回以上連続実行して同じ初期状態へ戻る。
- Client Action 後に自動 refresh されない画面は、成功メッセージを確認してから明示的に再読込する。
- 日付はテスト実行日依存を避けるため、固定日または十分な未来・過去の相対値を seed で設定する。
- おすすめ順は同点にならないスコアを使い、一覧順を決定的にする。

## テスト方針

実装は TDD で進める。

1. persona 解決と seed 巻き戻しのユニットテストを追加し、未定義・未初期化による RED を確認する。
2. persona と seed を最小実装して GREEN にする。
3. 活動完了履歴のユニットテストを追加し、`completed` 除外による RED を確認する。
4. 履歴の最小修正で GREEN にする。
5. Playwright O-E1〜O-E10 を追加する。
6. 対象 UT、全 UT、lint、型チェック、build、`make e2e` 2回連続を実行する。

## 完了条件

- O-E1〜O-E10 がテスト名から追跡できる。
- 既存 O1〜O3 が成功する。
- 変更系ケースが専用ペルソナ・専用レコードを使用する。
- `seed:e2e` が審査・案件・応募・アプローチ・証明書を初期状態へ戻す。
- persona と seed 巻き戻しにユニットテストがある。
- 活動完了がマッチング履歴へ表示される。
- 固定時間待機と CSS クラス依存セレクタを使用しない。
- lint、型チェック、全 UT、build、`make e2e` 2回連続が成功する。

## スコープ外

- Google OAuth、メール送信など外部サービスとの実通信
- 本番・Vercel Preview への破壊的テスト
- Issue #166 の共通認証・認可マトリクス
- 管理者向け機能の追加
- O-E9 の既存状態漏れ修正を除く、プロダクト機能の新規実装
