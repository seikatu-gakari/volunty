# Volunty 手動動作検証シナリオ設計

## 目的

Volunty の参加者・団体・管理者をまたぐ主要業務を、ローカル環境のブラウザ操作で検証する。
ロール別機能を個別に確認するだけでなく、同じ団体・案件・参加者・応募・証明書の状態がロール間で正しく引き継がれることを重視する。

## 採用方針

- 1本の正常系 `M-01` で、団体登録から参加証明書PDFの確認までを通す。
- 団体否認、応募辞退、アプローチ、アカウント凍結、認証・認可を重要分岐 `B-01`〜`B-05` として独立させる。
- 対象はローカル環境のみとし、各シナリオの開始前に `npm run seed:e2e` でE2E用データを初期化する。
- Google OAuthは対象外とし、`/api/test-auth/login` でペルソナを切り替える。
- 画面から観察できる結果を合否判定の一次情報とする。DBの直接確認は合格条件に含めない。

## 対象範囲

| ID | シナリオ | 主なロール |
| --- | --- | --- |
| M-01 | 登録から証明書発行までの正常系 | 団体・管理者・参加者 |
| B-01 | 団体申請の否認・理由確認・再申請 | 団体・管理者 |
| B-02 | 応募の辞退と連絡先の非開示 | 参加者・団体 |
| B-03 | 団体からのアプローチ承諾・辞退・期限切れ | 参加者・団体 |
| B-04 | アカウント凍結・強制退出・解除 | 参加者・管理者 |
| B-05 | ロール越境・他団体データ・未承認団体のアクセス制御 | 全ロール |

### 対象外

- Google OAuthの認証画面、コールバック、Googleアカウント選択
- Preview・本番環境と本番データ
- 性能・負荷試験
- 全画面・全viewportのビジュアル回帰
- メール送信や外部LINEサービスとの実通信

Google OAuth周辺は開発者が別途手動確認する。

## 実行前提

### 環境起動

プロジェクトルートで開発環境を起動する。

```bash
make up
```

別ターミナルから、各シナリオの開始前にE2E用データを初期化する。

```bash
cd app
npm run seed:e2e
```

途中でシナリオを中断した場合は、変更済みデータを手作業で修復せず、`npm run seed:e2e` を再実行して最初からやり直す。

### テスト認証

次のURLを開き、同じブラウザセッションのログインペルソナを切り替える。

```text
http://localhost:3000/api/test-auth/login?persona=<ペルソナ>&next=<遷移先>
```

`app/.env.local` で `E2E_AUTH_ENABLED=true` と `E2E_TEST_USER_PASSWORD` が設定されていることを前提とする。テスト認証ルートはproductionでは利用しない。

- 未承認・応募審査中の段階で非公開情報が表示されない。
- 証明書PDFがダウンロードでき、ファイルサイズが0バイトより大きい。
- PDF内の案件名、参加者名、団体名、証明書番号が画面表示と一致する。

## B-01 団体申請の否認・再申請

### 使用ペルソナ

- 管理者: `admin-review`
- 団体: `organization-review-reject`

### 検証内容

1. 管理者が審査待ちの `organization-review-reject` を開く。
2. 却下理由が空の間は「否認する」が無効であることを確認する。
3. 却下理由に「手動検証B01 不足情報を追記してください」と入力して否認する。
4. 審査一覧と履歴に「否認済み」、理由、審査者が表示されることを確認する。
5. 団体へ切り替え、否認状態と同じ理由が表示されることを確認する。
6. 「申請内容を修正する」から団体名末尾に「再申請」を付けて再申請する。
7. 「審査中です」に戻り、`/dashboard` が利用できないことを確認する。
8. 管理者が再申請を承認し、団体がダッシュボードを利用できることを確認する。

要件: O-2、O-2a、A-2、A-3、C-2。

## B-02 応募の辞退と連絡先の非開示

### 使用ペルソナ

- 団体: `organization-approved`
- 参加者: `participant-lifecycle`

### 検証内容

1. seed済みの「E2E 審査中応募案件」と審査中応募を使用する。
2. 参加者側で応募状態が「審査中」であり、団体LINE連絡先が非表示であることを確認する。
3. 団体側で応募メッセージと活動スタイルの参考情報を確認する。
4. 団体側に「BIG5 スコア詳細」が表示されないことを確認する。
5. 団体が応募を辞退する。
6. 参加者側で「辞退済み」となり、団体LINE連絡先が表示されないことを確認する。
7. 案件詳細に再応募ボタンが表示されず、同じ案件へ重複応募できないことを確認する。

要件: P-7、P-8、P-11、O-8、O-9。

## B-03 団体からのアプローチ

### 使用ペルソナ

- 団体: `organization-approved`
- 新規アプローチの受信参加者: `participant-onboarded`
- 辞退・期限切れ確認用の参加者: `participant-lifecycle`

### 検証内容

1. 団体が `participant-onboarded` をおすすめ参加者から開き、「E2E 応募対象案件」と「手動検証B03 アプローチメッセージ」を指定して送信する。
2. 送信履歴に対象参加者、案件、メッセージ、未回答状態が表示されることを確認する。
3. 同じ参加者・案件の選択肢が送信済みとなり、重複送信できないことを確認する。
4. `participant-onboarded` 側で直前のアプローチを承諾し、「承諾済み」と団体LINE連絡先が表示されることを確認する。
5. `participant-lifecycle` へ切り替え、seed済みの「E2E 辞退対象アプローチ案件」を辞退し、団体LINE連絡先が表示されないことを確認する。
6. 同じ参加者のseed済み「E2E 期限切れアプローチ案件」で、承諾・辞退ボタンが表示されないことを確認する。
7. 団体側の履歴で、直前に承諾されたアプローチと、seed済みの未回答・辞退済み・期限切れを確認する。

要件: O-5、O-6、O-7、P-9、P-10、P-11。

## B-04 アカウント凍結・解除

### 使用ペルソナ

- 管理者: `admin-review`
- 参加者: `user-suspendable`

### 検証内容

1. 管理者が `e2e-user-suspendable@example.com` を検索する。
2. 「凍結する」を選び、理由に「手動検証B04 凍結確認」と入力して確定する。
3. 管理画面で対象者が「停止中」と表示されることを確認する。
4. 参加者へ切り替えて `/mypage` を開く。
5. `/login?error=suspended` へ移動し、「このアカウントは凍結されています」と表示されることを確認する。
6. 管理者へ戻り、対象者の凍結を解除する。
7. 参加者として再度テスト認証し、マイページを利用できることを確認する。

シナリオが途中で失敗した場合も、終了前に凍結解除を試みる。解除できない場合は `npm run seed:e2e` を実行して `isActive=true` へ戻す。

要件: A-1、A-4、C-2。

## B-05 認証・認可・所有権

### 使用ペルソナ

- 参加者: `participant-onboarded`
- 承認済み団体: `organization-approved`
- 審査待ち団体: `organization-pending-readonly`
- 否認済み団体: `organization-rejected`
- 別団体: `organization-secondary`
- 管理者: `admin`

### 検証内容

1. 未認証状態で `/mypage`、`/dashboard`、`/admin` を開き、復帰先付きログイン画面へ移動することを確認する。
2. 参加者で `/dashboard` と `/admin` を開き、`/forbidden` になることを確認する。
3. 団体で `/mypage` と `/admin` を開き、`/forbidden` になることを確認する。
4. 管理者で `/mypage` と `/dashboard` を開き、`/forbidden` になることを確認する。
5. 審査待ち団体と否認済み団体で `/dashboard` を開き、審査状態画面へ戻されることを確認する。
6. 承認済み団体から自団体の案件編集、応募者詳細、証明書申請詳細のURLを記録する。
7. `organization-secondary` へ切り替えて記録したURLを開く。
8. 他団体の案件編集フォーム、応募者情報、証明書情報、承認・却下操作が表示されないことを確認する。
9. ログアウト後に保護画面を開き直し、ログイン画面へ戻されることを確認する。

認可違反、他団体データ、個人情報、更新操作の露出は、更新が失敗する場合でもFailとする。

要件: C-1、C-2、および案件・応募・証明書の所有権境界。

## 実施順序

1. M-01 正常系
2. B-01 団体否認・再申請
3. B-02 応募辞退
4. B-03 アプローチ
5. B-04 凍結・解除
6. B-05 認証・認可

各シナリオは独立しており、前のシナリオの変更結果を次の前提にしない。

## 実施記録

各手順を次の形式で記録する。

| 項目 | 記録内容 |
| --- | --- |
| 実施日時 | `YYYY-MM-DD HH:mm` |
| 実施者 | 名前または識別子 |
| commit | 検証対象のGit commit hash |
| シナリオID・手順ID | `M-01-01` など |
| 操作ロール | participant / organization / admin |
| 実施結果 | Pass / Fail / Blocked |
| 実際の結果 | 画面文言、URL、状態、表示・非表示 |
| 証跡 | スクリーンショット、PDF、必要に応じてログ |
| 不具合 | Issue番号または未登録 |

### 判定基準

- **Pass**: 期待結果をすべて満たし、次のロールへデータが正しく引き継がれる。
- **Fail**: 表示、状態、権限、データ引き継ぎのいずれかが期待と異なる。
- **Blocked**: 環境起動やseed失敗など、プロダクト操作前の問題で実施できない。

認可違反や非公開情報の露出は、後続操作を続けられる場合でも必ずFailとする。失敗した手順をPassへ読み替えず、修正後にseedからシナリオ全体を再実施する。

### 不具合記録の必須項目

- シナリオIDと手順ID
- 使用ペルソナ
- 期待結果
- 実際の結果
- 最小再現手順
- スクリーンショットまたは画面録画
- ブラウザと検証対象commit
- 必要に応じてブラウザコンソールとサーバーログ

## 完了条件

- M-01とB-01〜B-05の全手順にPass / Fail / Blockedの結果が記録されている。
- M-01の全手順がPassし、証明書PDFの内容まで確認されている。
- B-01〜B-05にFailがない。
- Blockedが残っていない。
- Failが発生した場合は、再現情報付きの不具合として記録されている。
- Google OAuthの確認結果は、本シナリオとは別の開発者確認記録として管理されている。
