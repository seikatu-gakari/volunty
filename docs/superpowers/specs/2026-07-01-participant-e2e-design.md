# 参加者向けE2Eテスト拡充 設計書

## 目的

Google OAuthそのものを除き、Voluntyの参加者向け機能 P-2〜P-14 とアカウント削除を、ローカルSupabaseとPlaywrightで再現可能なE2Eテストとして検証する。

既存の `participant.spec.ts` が確認しているオンボーディング誘導、おすすめ案件表示、応募、マイページ表示を維持しつつ、未検証の診断、プロフィール編集、検索条件、詳細画面、アプローチ、LINE連絡先、証明書、アカウント削除まで対象を広げる。

## 対象範囲

| 要件 | E2Eで確認する振る舞い |
| --- | --- |
| P-2 プロフィール登録 | 参加者ロールを選び、必須項目を入力して登録できる |
| P-3 性格診断 | 簡易16問と詳細60問を完了できる |
| P-4 診断結果表示 | 人物タイプとBIG5結果を表示できる |
| P-5 おすすめ案件 | 一覧表示とカテゴリ・地域・参加形態フィルターが機能する |
| P-6 団体詳細 | 案件から団体詳細へ遷移し、公開案件を確認できる |
| P-7 案件応募 | メッセージ付きで応募でき、重複応募を防止できる |
| P-8 応募状況 | マイページと応募詳細で状態を確認できる |
| P-9 アプローチ受信 | 受信一覧と詳細、回答期限を確認できる |
| P-10 アプローチ返信 | 未回答・期限内のアプローチを承諾または辞退できる |
| P-11 LINE表示 | 応募承認後またはアプローチ承諾後だけ連絡先を確認できる |
| P-12 証明書発行 | 活動完了済み応募から申請し、発行済みPDFをダウンロードできる |
| P-13 証明書一覧 | 申請中・発行済み・却下済みを一覧と詳細で確認できる |
| P-14 再診断 | 結果画面から再診断し、新しい結果へ更新できる |
| アカウント削除 | 専用参加者を物理削除し、ログイン画面へ遷移する |

OAuthプロバイダーとの通信、Googleアカウント選択画面、本番Supabase/Vercelは対象外とする。認証済み状態の準備には既存のローカル専用テスト認証ルートを使う。

## 採用方式

テスト順序による状態汚染を抑えるため、シナリオ別の参加者ペルソナを使用する。

| ペルソナ | 用途 | 初期状態 |
| --- | --- | --- |
| `participant-fresh` | ロール選択・プロフィール登録 | role未設定、オンボーディング未完了 |
| `participant-diagnosis` | 簡易・詳細診断、結果表示、再診断 | 参加者プロフィールあり、診断結果なし |
| `participant-onboarded` | おすすめ、詳細、応募、プロフィール編集 | 診断済みプロフィールあり |
| `participant-lifecycle` | 応募状態、LINE、アプローチ、証明書 | 状態別の応募・アプローチ・証明書あり |
| `participant-delete` | アカウント削除 | 削除可能な参加者プロフィールあり |

`participant-fresh` と `participant-onboarded` は既存定義を流用する。残り3件を追加し、`seed:e2e`を実行するたびにAuthユーザーとDB状態を冪等に再作成する。

## テスト構成

参加者E2Eを次のファイルへ分割する。

1. `participant-onboarding.spec.ts`
   - ロール選択からプロフィール登録まで
2. `participant-diagnosis.spec.ts`
   - 簡易診断、詳細診断、結果表示、再診断
3. `participant-discovery.spec.ts`
   - おすすめ一覧、フィルター、案件詳細、団体詳細、応募、応募状況、プロフィール編集
4. `participant-lifecycle.spec.ts`
   - LINE秘匿・開示、アプローチ承諾・辞退、証明書申請・一覧・詳細・PDF
5. `participant-account.spec.ts`
   - 専用ペルソナのアカウント削除

既存 `participant.spec.ts` のケースは、新構成へ移動するか重複しない形に整理する。各テスト名には対象要件IDを含める。

## Seedデータ

`seed-e2e.ts` に以下を追加する。

- 診断専用参加者プロフィール
- ライフサイクル専用参加者プロフィールと診断結果
- 削除専用参加者プロフィール
- フィルター確認用のカテゴリ・地域・参加形態が異なる公開案件
- pending、accepted、completedの応募
- 回答可能なアプローチ2件と期限切れアプローチ1件
- pending、issued、rejectedの証明書
- 発行済み証明書番号と発行日時

同一参加者・同一案件のUnique制約を守り、固定タイトルまたは固定識別子で既存データを検索してupsertする。変更系テストの初期状態は、毎回のglobal setupで必ず巻き戻す。

アカウント削除ペルソナは前回の実行でAuthユーザーごと消えていても、次回seedで新規作成される。

## テスト設計原則

- `waitForTimeout`は使わず、URL、見出し、ボタン状態、成功メッセージで同期する。
- role、label、headingなどアクセシブルなlocatorを優先する。
- 一つのテストは一つの利用者目的を検証する。
- 変更を伴うケースは専用レコードを使い、別ケースの前提データを破壊しない。
- PDFはPlaywrightのdownloadイベント、拡張子、Content-Typeまたはファイルサイズで確認する。
- LINE連絡先は未成立時に非表示、成立後に表示される両方を確認する。
- 簡易16問・詳細60問は実際の回答UIを操作し、Actionの直接呼び出しで省略しない。

## TDDと検証

1. Seed UTへ新ペルソナと再作成条件の期待を追加し、REDを確認する。
2. E2Eケースを追加し、未追加seedまたは未満足の画面状態でREDを確認する。
3. 最小限のpersona・seed変更でGREENにする。
4. 対象UT、全UT、lint、build、`make e2e`を実行する。

テストのみの変更であり、本番UIやServer Actionの振る舞いは原則変更しない。E2Eによって既存不具合が発見された場合は、原因と影響を報告し、テスト追加と本番修正の範囲を分けて判断する。

## 完了条件

- P-2〜P-14とアカウント削除が上記E2Eに対応付いている。
- 削除ペルソナが連続実行でも再作成される。
- 各テストが単独でも意図を理解できる名前とassertを持つ。
- UT、lint、build、E2Eの実行結果を報告できる。
- 実行不能または失敗が残る場合は完了扱いにせず、失敗箇所と残作業を明示する。
